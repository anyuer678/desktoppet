# 软件项目开发规范（扩展版）

---

# 一、版本管理规范

## 1. 版本号规则

格式：

```
大版本号.日期.构建编号
```

例如：

```
1.0.0803.01
```

含义：

| 字段   | 说明       |
| ---- | -------- |
| 1.0  | 功能大版本    |
| 0803 | 构建日期（月日） |
| 01   | 当天第几个构建  |

---

## 2. 大版本规则

### 主版本

格式：

```
1.0
1.1
1.2
```

用于：

* 新功能模块
* 架构调整
* UI大改
* 核心能力升级

例如：

```
1.0 初始版本

1.1 新增插件系统

1.2 新增AI能力
```

---

### 构建版本

用于：

开发过程记录。

例如：

```
1.0.0803.01
1.0.0803.02
1.0.0803.03
```

同一天多次测试：

只增加构建号。

---

# 二、更新日志规范

每次生成安装包必须包含：

```
CHANGELOG.md
```

格式：

```
Version:
1.0.0803.01

Date:
2026-08-03


新增：
- xxx功能

优化：
- xxx性能

修复：
- xxx问题


已知问题：
- xxx
```

---

## 更新类型分类

### 新增 Added

新功能。

例如：

```
新增桌宠状态系统
```

---

### 优化 Improved

已有功能提升。

例如：

```
优化动画加载速度
```

---

### 修复 Fixed

Bug修复。

例如：

```
修复窗口无法置顶问题
```

---

### 移除 Removed

删除功能。

---

# 三、开发版本与正式版本规范

## 开发版本

特点：

* 高频更新
* 功能测试
* 不保证稳定

例如：

```
1.0.0803.01
1.0.0803.02
```

用途：

内部测试。

---

## 正式版本

条件：

满足：

* 核心功能完成
* 无严重Bug
* UI稳定
* 安装测试完成

版本：

```
1.0 Release
```

例如：

```
DesktopPet 1.0
```

---

正式版需要：

保存：

```
Release/

├── 安装包
├── 更新日志
├── README
├── 使用说明
└── 源代码备份
```

---

# 四、代码备份规范

## 触发条件

以下情况必须备份：

### 1. 新功能开发前

例如：

新增：

* 插件系统
* 数据库
* AI模块

操作：

```
backup_before_feature_xxx
```

---

### 2. 架构修改前

例如：

* 重构目录
* 更换框架
* 修改核心逻辑

---

### 3. 正式版本发布前

---

## 备份内容

必须包含：

```
项目源码

配置文件

资源文件

数据库结构

依赖版本

编译说明
```

---

## 实际操作约定（项目现行）

- 备份目录 `backup/`：每个大版本一个最终快照目录 `v<大版本>-final`（对应 `CHANGELOG.md` 该版本段，`package.json` 版本号可核对真实版本）；历史中间快照归档于 `backup/_archive/`，不参与最终版对照。
- 发版收盘刷新对应 final：`node .superpowers\sdd\copy-backup.js "backup\v<大版本>-final"`（脚本拷贝 src/docs/CHANGELOG/package*/启动/自检/构建验证脚本）。
- 备份命名以目录名与 `backup/README.md` 对照表为准；旧目录如曾以 `-complete`/`-final` 宣称最终版但实际早于该版本后续构建，以 `package.json` 真实版本为准，勿沿用旧名。

# 五、UI设计规范

## 核心原则

避免：

> AI生成感

表现：

* 默认圆角卡片堆叠
* 大量渐变
* 无意义玻璃效果
* 模板化Dashboard

---

## UI要求

### 1. 有设计语言

项目必须确定：

* 色彩体系
* 字体体系
* 间距规范
* 图标规范

例如：

桌宠：

```
低饱和
自然色
轻拟物
```

---

### 2. 组件统一

禁止：

一个页面一种风格。

统一：

* 按钮
* 输入框
* 卡片
* 弹窗
* 动画

---

### 3. 动效规范

动画目的：

提升反馈。

不是：

为了炫技。

例如：

正确：

```
点击按钮
→轻微缩放
→反馈完成
```

错误：

```
打开设置
→整个页面飞入旋转
```

# 六、开发流程规范

## 阶段1：需求设计

输出：

```
功能说明

用户流程

UI设计

数据结构

接口设计
```

---

## 阶段2：原型

完成：

* 页面结构
* 基础交互
* UI确认

不进入复杂开发。

---

## 阶段3：功能开发

顺序：

```
核心逻辑

↓

数据

↓

接口

↓

UI

↓

优化
```

---

## 阶段4：测试

检查：

### 功能

* 是否完成需求

### 性能

* CPU占用
* 内存占用
* 启动速度

### 异常

* 崩溃
* 数据丢失
* 网络异常

---

# 七、发布规范

发布前：

检查：

```
□ 版本号正确

□ 更新日志完成

□ 安装包测试

□ 卸载测试

□ 配置迁移测试

□ 核心代码备份
```

---

# 八、Git规范

正式版上传GitHub。

结构：

```
Repository

├── README.md

├── CHANGELOG.md

├── LICENSE

├── docs

├── src

└── release
```

---

## Tag规范

正式版本：

```
v1.0
v1.1
```

开发版本：

不打正式Tag。

---

# 九、文档规范

每个中大型项目必须包含：

```
docs/

├── 开发文档

├── 架构设计

├── API说明

├── 更新记录

└── 部署说明
```

---

# 十、AI辅助开发规范

AI生成内容必须经过：

```
需求确认

↓

结构设计

↓

代码生成

↓

人工检查

↓

重构优化
```

禁止：

直接复制AI大段代码进入主项目。

---

# 十一、项目完成标准

一个项目达到发布标准：

必须具备：

## 软件层面

* 稳定运行
* 基础异常处理
* 配置管理

## 产品层面

* 完整UI
* 图标
* 安装包

## 工程层面

* 版本管理
* 更新日志
* 文档
* Git仓库

---

最终形成：

```
开发设计
    ↓
原型
    ↓
开发版本
    ↓
测试
    ↓
正式版本
    ↓
GitHub Release
```
